# Семь исправленных дефектов выпуска модели и API

В исходном прототипе ошибки затрагивали подготовку данных, допуск и публикацию модели, готовность сервиса и обработку запросов. Ниже разобраны семь независимых причин из [defects.csv](defects.csv). Для каждой сохранён регрессионный тест, который выявляет ошибку исходника и проходит после исправления.

## D1. Кеш подготовки не замечал изменения данных

Исходная `cache_key` хешировала строку пути. После изменения байтов `input.txt` по тому же пути подготовка возвращала `CACHE_HIT` со старым результатом. Настройки токенизатора, шаблона, длины и обработки также не участвовали в ключе.

В [release.py](../release.py) ключ вычисляется из SHA256 содержимого и канонического JSON всей конфигурации. Одинаковые байты в разных путях дают одинаковый ключ; порядок полей словаря его не меняет. В [lab.py](../lab.py) подготовка дополнительно учитывает фактический SHA кода обработки. Результат сохраняется на диске, а задача Prefect использует `persist_result=True`.

После сбоя за подготовкой новый процесс использует сохранённый результат. Изменение содержимого по прежнему пути или любого параметра подготовки даёт новый ключ и `PREPARED`.

**Подтверждение:** `test_process_cache_recovery_and_input_change`; журналы [восстановления](../evidence/logs/flow-recovery.log) и [изменения входа](../evidence/logs/flow-change-input.log) показывают состояния `Cached` и `Completed`.

## D2. Незаконченный или чужой отчёт разрешал выпуск

Исходная `validate_release` проверяла только истинность `passed`. Непустая строка `"false"` считалась успешным решением. Отчёт со статусом `running` и отчёт модели A для кандидата B могли изменить принятый указатель.

В [release.py](../release.py) проверяются полная обязательная схема, `status="complete"`, именно `passed is True`, непустой evaluation run ID, конечные метрики и совпадение идентификатора модели и хешей. Хеш runtime пересчитывается из его содержимого. Отсутствующие поля, NaN/Inf и несовместимость закрывают выпуск.

Для настоящей модели [gate.py](../gate.py) дополнительно проверяет SHA исходных отчётов и ответов, заново вычисляет score и вызывает сохранённое правило качества ДЗ 6–7. У кандидата подтверждена регрессия accuracy, поэтому отказ сохранён, а API обслуживает закреплённую baseline.

**Подтверждение:** `test_process_rejection_incomplete_and_foreign_report`; [решение кандидата](../evidence/model-synced/release-report.json) и [SHA accepted.json до и после отказа](../evidence/model-synced/refusal-pointer.json).

## D3. Указатель принятой модели записывался напрямую

Прототип перезаписывал `accepted.json` через `write_text`. При прерывании записи файл мог оказаться неполным. Проверка с mock ошибки `os.replace` не влияла на выпуск: атомарная замена вообще не вызывалась, команда завершалась успешно и меняла указатель.

В [release.py](../release.py) сначала выполняется проверка допуска. JSON записывается во временный файл рядом с целевым, затем выполняются `flush`, `fsync` и `os.replace`. При ошибке замены исключение передаётся вызывающему коду, временный файл удаляется, прежний указатель сохраняется.

**Подтверждение:** `test_process_atomic_disk_error_preserves_pointer` вносит ошибку замены через mock в отдельном процессе. Исправленный выпуск возвращает ненулевой код, SHA прежнего файла остаётся тем же, временные файлы отсутствуют. Приложенный `test_failed_atomic_replace_preserves_previous_bytes` проверяет этот контракт отдельно.

## D4. Повтор выпуска размножал публикации

Каждый успешный запуск безусловно добавлял строку в `publications.jsonl`. Три одинаковых выпуска B создавали три события. Устойчивого идентификатора и механизма согласования журнала с указателем не было.

В [publication.py](../publication.py) `release_id` вычисляется по manifest и связанному решению допуска. Он учитывает модель, runtime и оценку. Журнал попыток отделён от событий выпуска: повтор процесса создаёт новую попытку, но сохраняет одно событие той же версии.

Перед заменой указателя сохраняется durable intent. Если процесс падает после обновления `accepted.json`, но до записи события, следующий запуск сверяет хеш указателя, восстанавливает событие и очищает intent. `release-state.json` хранит основной журнал, а JSONL восстанавливается из него.

**Подтверждение:** `test_process_repeated_publication_is_one_event` и `test_crash_between_pointer_and_event_recovers_once`; журнал [восстановления после сбоя](../evidence/logs/flow-crash-recovery.log) содержит `RECOVERED_PUBLICATION`, последующий повтор не создаёт второе событие B.

## D5. Сервис объявлял готовность до прогрева

В исходном `ServiceState` значение `ready=True` устанавливалось сразу. `/ready` и `/generate` возвращали успех, пока фоновый прогрев ещё не завершился. Проверка жизни процесса подменяла проверку готовности модели.

В [service.py](../service.py) сервис начинает с `ready=False`. Фоновая загрузка проверяет manifest и файлы, создаёт backend и выполняет его `warmup`. Только после завершения этих действий устанавливается готовность.

Во время загрузки `/health` может возвращать 200, но `/ready` и `/generate` отвечают 503. После прогрева доступна генерация. Ошибка загрузки сохраняет состояние неготовности.

**Подтверждение:** `test_http_ready_waits_for_warmup` проверяет реальные HTTP-ответы до и после прогрева и один вызов backend на валидный запрос. `test_changed_artifact_rejected_before_publication_and_load` отдельно проверяет отказ готовности при повреждённом артефакте.

## D6. Метаданные ответа показывали незагруженную версию

После запуска на A прототип продолжал генерировать через backend A, но при каждом запросе заново читал `accepted.json`. Публикация B меняла `model_id` ответа на B, хотя сам текст оставался ответом A.

В [service.py](../service.py) принятие manifest и загрузка backend образуют снимок состояния процесса. Ответ получает `model_id` и `runtime_sha256` из фактически загруженного backend. Замена указателя на диске сама по себе не меняет модель в памяти.

HTTP-опыт подтверждает последовательность: A до публикации, A после публикации B без перезапуска, B после перезапуска, A после возврата принятой A и нового запуска. Это две явно помеченные STUB-версии. У настоящей модели отдельно подтверждены загрузка и перезапуск текущей baseline; второй реально допущенной версии нет.

**Подтверждение:** `test_http_loaded_version_restart_and_rollback`; [HTTP/process trace](../evidence/logs/final-integration-fixed.jsonl), [управляемый откат](../evidence/logs/flow-controlled-rollback.log) и [перезапуск реальной модели](../evidence/synced-api/api/restart.json).

## D7. Неверный запрос запускал вычисление

Прототип вызывал `backend.generate` до проверки параметров. Пустой prompt, нулевой или чрезмерный лимит и строка вместо числа могли получить 200 и увеличить счётчик вызовов backend.

В [service.py](../service.py) сначала проверяются форма JSON, поля, типы, непустота и длина prompt, затем готовность и соответствие лимита протоколу. Для реального backend проверяется также токенная длина входа вместе с шаблоном. Генерация начинается после этих проверок.

Допускается только оценённый `max_new_tokens=32`; bool и строка не считаются целым числом. Неверный запрос получает 4xx без вызова генерации. Ввод ограничен 8192 символами, 1024 токенами с шаблоном и телом запроса 65536 байт.

**Подтверждение:** `test_http_bad_request_never_calls_backend` проверяет неизменность `/debug.calls` для неверных запросов и увеличение на один после валидного. В [реальном smoke](../evidence/synced-api/api/real-response.json) чрезмерный лимит получает 422 при счётчике 0 → 0.

## Результаты проверок

Семь интеграционных регрессий на исходном прототипе завершаются assertion failures: [красный журнал](../evidence/logs/final-integration-original.log). На исправленном проекте они входят в общий успешный прогон **35/35**: [зелёный журнал](../evidence/logs/final-check-all.log).

Команды запуска из корня ДЗ:

```bash
HW8910_PROJECT=evidence/original .venv/bin/python -m unittest discover -s tests -p test_integration.py -v
make check
```

Первая команда ожидаемо возвращает 1, вторая — 0. Имена регрессий и отдельные команды воспроизведения каждой причины сохранены в [defects.csv](defects.csv).
