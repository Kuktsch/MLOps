# Четыре дефекта части A

## 1. Разные конфигурации смешивались в одном run

В исходном `src/sweep.py` один дочерний `all-candidates` охватывал весь цикл.
`run_candidate` записывал params только в пустой run, а затем обновлял теги,
кривые и файлы других моделей в той же записи. Логи переставали описывать
один эксперимент, а адаптер не соответствовал первоначальным параметрам.

Контекст `mlflow.start_run(..., nested=True)` перенесён внутрь цикла и получает
имя конфигурации. Родитель хранит общую таблицу; каждая конфигурация имеет
свой run_id, параметры, кривые 0/2/4, модельный пакет и генерации.
Доказательство: `metrics/sweep.json`, `docs/comparison.csv`, проверка 1/9.

## 2. Артефакты исчезали после замены контейнера

PostgreSQL имел volume, но `/mlartifacts` находился в слое контейнера.
Объявленный volume `artifacts` не был подключён. Сохранённые в Postgres
записи могли ссылаться на уже исчезнувшие веса.

В `compose.yaml` добавлено `artifacts:/mlartifacts` для сервиса MLflow.
Сервер передаёт файлы клиентам через HTTP. `make check-storage` записывает
новый случайный probe, пересоздаёт только MLflow проекта `mlops-hw6`
через `--force-recreate`, скачивает файл и сравнивает SHA256.
Доказательство: `metrics/storage-check.json`, проверка 8/9. База и volumes
при проверке не удаляются; другие compose-проекты не затрагиваются.

## 3. Версии train/val намеренно удалялись из provenance

`provenance` вычислял SHA256 обоих файлов, но `sweep.main` отбрасывал все
ключи с префиксом `data_`. Одинаковые пути не означают одинаковые данные;
проверить сравнимость запусков и соответствие текущим тензорам было нельзя.

Фильтр удалён. В parent и всех дочерних runs записываются полный Git SHA,
git_dirty, code_sha256, config_sha256, data_train_sha256, data_val_sha256.
Ревизия Qwen закреплена в конфиге и сохраняется в manifest/base_revision;
исходники и uv.lock отправляются в MLflow. Исходные JSONL, тензоры и набор
оценки отдельно версионируются DVC. Связь тензоров с raw проверена повторной
токенизацией всех примеров, см. `metrics/tokenization-proof.json`.

git_sha фиксирует HEAD репозитория на момент запуска. Значение
git_dirty=True указывает на незакоммиченные изменения. SHA256 и снимки
исходных файлов определяют фактически выполненную версию реализации.

## 4. Регистрация обходила порог loss

Функция `gate` была написана, но `promote` просто делил две метрики и сразу
создавал версию/alias. Даже кандидат с положительным loss проходил порог 0.

`promote` вызывает `gate(run, threshold)` до любых изменений реестра.
Проверяются FINISHED, finite loss/threshold, положительный base loss и
final/base ≤ max_val_ratio. Отказ не создаёт версию и не меняет alias.
Преподавательская проверка 6/9 вызывает promote с нулевым порогом.
Штатная регистрация создаёт `candidate`; выпуск `champion` проходит
дополнительную проверку ответов через `evaluation.cli promote`.

## Оценка и отрицательная проверка

`score` сопоставляет строки по уникальным id, строго разбирает JSON с одним
ключом answer и отвергает повторяющиеся ключи. Все ответы остаются в n;
валидная неверная метка отличается от ошибки формата и ошибки генерации.
Counts вычисляются из per_item для общей группы и каждого среза.

`quality_gate` проверяет совместимость протокола, полноту, counts/rates,
id, принадлежность срезам, ошибки генерации и отсутствие регрессии.
Допуск требует успешного прохождения всех behavioral-кейсов кандидата. В штатной обвязке метрики
повторно вычисляются из raw и сверяются хеши перед выпуском.
Отрицательная проверка повреждает отдельную копию raw, пересчитывает и
golden, и behavioral через тот же scorer; исходные ответы, веса и alias
не меняются. Это устраняет несогласованность counts/per_item при ручной
подмене одного behavioral-count в исходной вспомогательной команде.
